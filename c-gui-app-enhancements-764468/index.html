C++ desktop GUI audit

Abhishek Rana. A sketch of how the build would go.

The problem

A desktop application already runs. The GUI and the logic behind it need a focused pass: leftover bugs, polish or small extensions to current features, and a more responsive interface on a modern Windows machine. The first step is to clone the repository, compile it locally, and audit where time is going. The update list is agreed before edits. The toolkit may be Qt, wxWidgets, or a native Windows framework. The hand-off is commented source, a short change log, build steps that work on a fresh Windows machine, and an executable that keeps the old behavior plus the agreed upgrades.

Flow

  1. Clone the repo and produce a clean Windows build.
  2. Run the app and time the calls that sit on the UI thread.
  3. Agree a short update list from the slowest calls and the known bugs.
  4. Change only those spots, and move heavy work off the UI thread.
  5. Write the change log, the build steps, and ship the executable for an interim test.

Files

  • CMakeLists.txt is the fresh-machine build for the Windows executable.
  • src/audit.cpp records how long a named UI call took and returns the ones over budget.
  • src/main.cpp stays the existing entry point. New work is called from here only after the list is agreed.
  • CHANGELOG.md says what changed and why, in the order the builds were tested.
  • BUILD.md is the Windows compile and run note for a clean machine.

Architecture

The audit runs against the current binary before features change. Each timed call is a name plus microseconds. Calls under the frame budget stay off the list. Calls over the budget are sorted slowest first, and only the top few are proposed. After that list is agreed, heavy work moves off the UI thread and the screen still shows the same results. Qt, wxWidgets, or the native Windows toolkit is taken from the repo, not guessed. The change log and the build note travel with the executable. This is a sketch of that pass. It is not a claim that a particular application has already been updated.

Rank the slow calls

#include <algorithm>
#include <string>
#include <vector>

struct Sample {
    std::string name;
    long long us;
};

std::vector<Sample> slow_calls(std::vector<Sample> rows, long long budget_us, std::size_t limit) {
    std::vector<Sample> slow;
    for (const Sample& row : rows) {
        if (row.us > budget_us) {
            slow.push_back(row);
        }
    }
    std::sort(slow.begin(), slow.end(), [](const Sample& a, const Sample& b) {
        if (a.us != b.us) {
            return a.us > b.us;
        }
        return a.name < b.name;
    });
    if (slow.size() > limit) {
        slow.resize(limit);
    }
    return slow;
}

On four samples with a 16 ms budget (16000 microseconds) and a limit of 2, the result is paint_table at 42000 us, then reflow_panel at 18000 us. load_file at 8000 us and status_bar at 400 us stay off the list. Two calls with the same time are ordered by name. This compiled and ran with g++ in C++17.
