WhatsApp Cloud API for a multi-tenant SaaS

Abhishek Rana. Messaging services in production, including platform work at Microsoft.

Each organisation connects its own WhatsApp Business Account. The app stores that tenant's WABA id, phone number id, and token. A campaign sends only an approved template. The webhook writes delivered, read, or failed back onto the same message row.

1. Embedded Signup2. Token stored per tenant3. Template must be approved4. Queue sends a batch5. Webhook updates status

Files

signup.js finishes Embedded Signup and writes the three ids on that tenant only. templates.js reads Graph and stores approved, pending, or rejected. queue.js is the only file that calls send. webhook.js verifies the payload and updates the log. The Next.js page never holds the token.

Architecture

Next.js for the org admin. Node API for signup, templates, and the campaign row. MySQL tables are all keyed by tenant id: accounts, contacts, templates, campaigns, messages. A worker pulls a small batch, calls the Cloud API, and stores the returned message id. A rate-limit error goes back on the queue with a delay. STOP is checked before the send, so an opted-out number never enters the batch.

function enqueue(tenant, template, contacts) {
  if (template.status !== "approved") return "template_not_approved";
  const allowed = contacts.filter(c => !c.opted_out && c.tenant_id === tenant.id);
  return db.insert("outbox", allowed.map(c => ({
    tenant_id: tenant.id,
    phone_number_id: tenant.phone_number_id,
    to: c.phone,
    template: template.name,
    state: "queued"
  })));
}

The lookup key on the webhook is phone_number_id. That is how one business stays isolated from the next.
