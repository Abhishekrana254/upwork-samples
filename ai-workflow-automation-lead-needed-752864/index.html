Automation Anywhere agent step

Abhishek Rana. A sketch of how the build would go.

The problem

A programme needs large-language-model reasoning and an agent layer inside Automation Anywhere. Several labour-intensive processes should become workflows that run on their own and can be watched. The work starts with an architecture map, then a proof on one process, then production, with a small in-house team. Prompts, model hosting or fine-tuning (OpenAI, Anthropic, Hugging Face, or similar), and a call from an Automation Anywhere package or a REST step are in scope. LangChain or a similar stack can sit behind that call. Success is decision accuracy, latency, and clean code in Git, with tasks in Jira and one-week sprints. The hand-off is a blueprint, one bot that finishes the chosen workflow, a knowledge-transfer note, and a live walkthrough.

Flow

  1. Pick one process and write the blueprint: components, data flow, and security.
  2. Define the decision the agent must return, and the latency budget.
  3. Expose that decision as a REST call the Automation Anywhere bot can make.
  4. Score each run for accuracy against a known label, and record latency.
  5. Walk the in-house team through the bot, the prompt, and the Git history.

Files

  • blueprint.md lists every component, the data flow, and the security notes (keys, logs, what the bot may see).
  • prompts/decision.txt is the prompt for the chosen model. The rule check below still runs after the model replies.
  • agent/decide.py turns one case into approve, review, or handoff, then scores accuracy and latency.
  • agent/app.py is the FastAPI route the bot calls. It returns the action, the reason, and the timing.
  • aa/bot_steps.md is the Automation Anywhere bot: read the case, call the REST route, write the result, stop for a person on handoff.
  • README.md covers how to run the service, where the daily score is stored, and what the walkthrough should show.

Architecture

Automation Anywhere stays the runner. It sends one case to a small Python service and waits for a structured action. The model may draft a reason. decide.py still applies the business rule, so a missing field or a bad amount cannot be approved. Each call stores whether the action matched the gold label and whether it finished inside the latency budget. Secrets stay in the Automation Anywhere credential store, not in the bot file and not in Git. The first bot covers one process only. Other processes reuse the same route with a different prompt and limit. This is a sketch of that first bot. It is not a claim that the programme is already running.

Score one decision

def decide(case, limit=5000):
    required = ("id", "vendor", "amount")
    missing = [key for key in required if case.get(key) in (None, "")]
    if missing:
        return "handoff", "missing"
    amount = case["amount"]
    if not isinstance(amount, (int, float)) or amount < 0:
        return "handoff", "amount"
    if amount > limit:
        return "review", "over_limit"
    return "approve", "within_limit"

def judge(action, gold, elapsed_ms, max_ms=1500):
    correct = action == gold
    within = elapsed_ms <= max_ms
    return {
        "correct": correct,
        "latency_ms": round(elapsed_ms, 1),
        "within_budget": within,
        "pass": correct and within,
    }

A case with a blank vendor is handoff. Amount 9000 against a 5000 limit is review. Amount 100 is approve. An approve that matches the gold label in 400 ms passes. The same approve at 2000 ms fails the latency budget. An approve when the gold label is review fails accuracy. Those checks are what the bot log would keep.
